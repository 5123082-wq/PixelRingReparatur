## Порядок выпуска после подтверждения

1. Зафиксировать подготовленную ветку, отправить её на GitHub и создать запрос на слияние в актуальную основную ветку. Если основная ветка изменилась после `af421e4`, сверить новые изменения перед выпуском.
2. Для предварительного развёртывания использовать отдельную тестовую базу с применённой миграцией. Не подключать сквозные тесты и команды начального наполнения к рабочей базе.
3. Проверить целевую базу, состояние миграций и доступность точки восстановления. Единственная новая миграция этого пакета — `20260925120000_intake_email_verification` (таблица одноразовых подтверждений почты). Если обнаружены другие ожидающие миграции, сначала выяснить причину.
4. После отдельного разрешения на рабочую базу выполнить из каталога приложения `npm run db:status` (проверку состояния), затем `npm run db:deploy` (применение миграций), затем повторную проверку состояния. Скрипт использует `DIRECT_URL` (прямой адрес базы) либо `POSTGRES_URL_NON_POOLING` (адрес без пула соединений); значения не выводить и не записывать в отчёт. Команда применения запускает все ожидающие миграции, а не одну выбранную.
5. Новая миграция только добавляет таблицу `intake_email_verifications` (одноразовых подтверждений) и три индекса; существующие таблицы и данные не удаляет. Применить её до включения нового кода на рабочем сайте. Не запускать команды начального наполнения рабочей базы.
6. Проверить имеющуюся почтовую конфигурацию: `PORTAL_EMAIL_PROVIDER` (поставщик почты), `PORTAL_EMAIL_FROM` (адрес отправителя) и настройки действующего поставщика SMTP (почтового сервера) либо Resend (сервиса отправки). Новый сценарий использует существующий механизм; новых обязательных имён переменных пакет не добавляет.
7. После разрешения на публикацию слить запрос в основную ветку и дождаться успешного рабочего развёртывания Vercel. Проверить соответствие опубликованного коммита согласованному пакету и привязку рабочего домена.
8. Проверить главную, галерею, форму, LED-страницу, шесть языков и сохранение языка юридических ссылок. Через контролируемый тестовый почтовый ящик проверить получение кода, повторную гостевую заявку с вложением, отсутствие нового аккаунта/прав, сохранность предыдущей заявки и отказ повторного использования подтверждения. Проверить две одновременные отправки в целевой PostgreSQL (рабочей системе базы данных): успешной должна быть одна.
9. Просмотреть журнал ошибок нового развёртывания. Подтвердить выпуск и обновить глобальный и доменные журналы после фактической проверки.
