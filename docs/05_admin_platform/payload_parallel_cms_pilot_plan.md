# Параллельный пилот Payload CMS для Referenzen

## Статус документа

- Дата решения владельца: 2026-07-20.
- Статус: архитектура утверждена владельцем, реализация ещё не начата.
- Первый пилотный объект: `Referenzen` (страница примеров работ).
- Действующий источник публичного контента до отдельного переключения: существующие `CmsPage` и `CmsMedia`.
- Новая система: Payload CMS (новая система управления публичным контентом).
- Основной принцип: параллельное внедрение без удаления, остановки или скрытой перезаписи существующей CMS.

Этот документ заменяет прежнее общее ограничение «не использовать внешнюю CMS» только в отношении постепенно переносимого публичного контента. Он не разрешает замену CRM (системы работы с заявками), AI Knowledge (управления знаниями для ИИ), клиентского кабинета или других операционных модулей.

## 1. Решение владельца

PixelRing начинает отдельный контролируемый пилот Payload CMS (новой системы управления публичным контентом), сохраняя текущую CMS в рабочем состоянии.

Утверждённая модель:

1. Текущий `signage-service` продолжает обслуживать публичный сайт, CRM (систему работы с заявками), старую CMS и остальные существующие функции.
2. Новое приложение `content-studio/` создаётся в том же репозитории, но запускается и собирается отдельно.
3. Локальная версия `Referenzen` (страницы примеров работ) постепенно подключается к Payload CMS (новой системе управления публичным контентом).
4. Рабочий сервер продолжает читать `Referenzen` (страницу примеров работ) из старой CMS до завершения локальной разработки, импорта, проверки и отдельного решения владельца о переключении.
5. Старая CMS не удаляется после первого переключения и остаётся доступной как контролируемый резерв до завершения периода наблюдения.

## 2. Почему выбран Payload

Payload выбран вместо дальнейшего расширения кастомного редактора и вместо Strapi по следующим причинам:

- бесплатная самостоятельная эксплуатация по MIT License (свободной коммерческой лицензии);
- нативная совместимость с Next.js 16.2.6 и TypeScript;
- встроенные Media Collections (медиаколлекции), локализация, черновики, версии, восстановление и Live Preview (живой предпросмотр);
- явная поддержка RTL (направления справа налево) для арабского языка;
- официальный адаптер Vercel Blob (файлового хранилища Vercel);
- возможность использовать существующие инфраструктурные сервисы без покупки отдельной CMS-лицензии;
- строгие схемы в коде вместо нового свободного конструктора страниц.

Официальные технические ориентиры:

- <https://payloadcms.com/docs/getting-started/installation>
- <https://payloadcms.com/docs/versions/overview>

## 3. Границы пилота

### Входит в пилот

- отдельное локальное приложение `content-studio/`;
- административный вход владельца;
- Media (медиатека) для публичных фотографий;
- структурированная модель `Referenzen` (страницы примеров работ);
- DE, EN, RU, TR, PL и AR;
- немецкий язык как канонический первый язык;
- арабский RTL (направление справа налево);
- Hero (главный экран), теги, секции, кейсы, галереи, фотографии, Alt-тексты (альтернативные описания), подписи, ссылки, видимость и SEO-поля (поля поисковой оптимизации);
- черновик, публикация, версии, восстановление и предпросмотр;
- безопасный экспорт текущего контента и импорт копии в Payload CMS (новую систему управления публичным контентом);
- локальный переключатель источника `legacy` (старая CMS) / `payload` (новая CMS);
- закрытая серверная проверка перед публичным переключением;
- документированный rollback (откат).

### Не входит в пилот

- перенос CRM (системы работы с заявками);
- перенос AI Knowledge (управления знаниями для ИИ);
- перенос статусов заявок, клиентского кабинета или Telegram-процессов;
- удаление текущих `CmsPage` или `CmsMedia`;
- двусторонняя синхронизация двух CMS;
- перенос всех страниц одновременно;
- универсальный drag-and-drop page builder (свободный визуальный конструктор страниц);
- изменение рабочего сервера до прохождения локальной приёмки;
- commit (фиксация в Git) или deployment (размещение на сервере) без отдельного подтверждения владельца.

## 4. Целевая архитектура

```text
PixelRingReparature/
├── signage-service/        # действующий сайт, CRM и старая CMS
└── content-studio/         # новое отдельное приложение Payload CMS
```

```text
Публичный маршрут /[locale]/referenzen
                    |
                    v
          Referenzen content adapter
          (адаптер источника контента)
              /             \
             /               \
      legacy source       payload source
      (старая CMS)        (новая CMS)
```

Технически Payload допускает установку в существующее Next.js-приложение. Для PixelRing выбран отдельный `content-studio/`, потому что это:

- уменьшает область риска для работающего сайта;
- не смешивает маршруты, cookies (файлы сессии), зависимости и сборки;
- позволяет развивать и тестировать новую CMS независимо;
- упрощает откат;
- не требует немедленно менять текущий `signage-service/package.json`, где уже есть незавершённые локальные изменения.

## 5. Разделение ответственности

| Область | Источник во время пилота | Целевой источник после приёмки |
|---|---|---|
| Публичная `Referenzen` (страница примеров работ) | Старая CMS на сервере, Payload локально | Payload CMS |
| Другие публичные страницы | Старая CMS и текущие источники | Без изменений до отдельного пилота |
| Публичные фотографии `Referenzen` (страницы примеров работ) | Текущие `CmsMedia` / Blob URLs (адреса файлов) | Payload Media |
| Заявки и CRM (система работы с заявками) | `signage-service` | `signage-service` |
| AI Knowledge (управление знаниями для ИИ) | `signage-service` | `signage-service` |
| Административные пользователи старой CMS | Текущая модель | Без изменений |
| Пользователи Payload | Отдельная Payload Auth (авторизация Payload) | Отдельная Payload Auth на первом этапе |

После переключения конкретная страница имеет только один редактируемый источник. Одновременное редактирование `Referenzen` (страницы примеров работ) в обеих CMS запрещено процессом, даже если старая запись ещё сохранена.

## 6. PostgreSQL без отдельного сервиса

Отдельный платный PostgreSQL-сервис не требуется.

Приоритетная серверная схема:

1. Использовать тот же PostgreSQL-кластер или проект, который уже обслуживает PixelRing.
2. Создать отдельную логическую базу для Payload, если текущий провайдер поддерживает это без нового сервиса.
3. Если отдельная логическая база недоступна, использовать отдельную схему `payload` и отдельную роль базы данных.
4. Не смешивать управляемые Payload-таблицы с Prisma-таблицами в общей схеме `public`.

Обязательные ограничения при общей базе:

- отдельный пользователь базы данных для Payload;
- права только на Payload-базу или Payload-схему;
- отсутствие прав изменения текущих Prisma-таблиц;
- автоматический `db push` (автоматическое изменение схемы) запрещён для production (рабочего окружения);
- production (рабочее окружение) изменяется только проверенными миграциями;
- перед первой серверной миграцией обязательна резервная копия и проверяемый план восстановления.

Локальная разработка не должна записывать данные в production-базу (рабочую базу). Для неё используется локальная или отдельная development-база (база разработки) с импортированной копией контента.

## 7. Vercel Blob без отдельного хранилища

Отдельный Vercel Blob Store (файловое хранилище Vercel) не требуется.

В существующем хранилище используются разные префиксы:

```text
cms-media/...                 # файлы текущей CMS
payload/development/media/... # локальная/тестовая интеграция, если подключено облачное хранилище
payload/production/media/...  # рабочие файлы Payload после размещения
```

Обязательные правила:

- локальный первый этап по умолчанию использует локальное файловое хранилище, а не рабочий Blob;
- подключение к рабочему Blob требует отдельного подтверждения владельца;
- загрузка Payload разрешена только внутри Payload-префикса;
- операция удаления проверяет Payload-префикс перед обращением к Blob;
- старые файлы копируются, а не перемещаются;
- `cms-media/...` не становится автоматически управляемой областью Payload;
- удаление используемого файла блокируется;
- ключи и Blob-токены не выводятся в логи и не передаются клиентскому коду.

Префикс является логическим разделением, а не полноценной границей прав токена. Поэтому серверная проверка пути обязательна.

## 8. Переключение источника контента

Предварительный контракт:

```text
REFERENZEN_CONTENT_SOURCE=legacy
REFERENZEN_CONTENT_SOURCE=payload
```

Правила:

- значение по умолчанию для production (рабочего окружения) до приёмки — `legacy` (старая CMS);
- локальная разработка пилота использует `payload` (новую CMS);
- неизвестное или отсутствующее значение не должно случайно включать Payload на сервере;
- во время локальной интеграционной проверки ошибка Payload показывается явно и не маскируется скрытым fallback (резервным возвратом) на старую CMS;
- закрытый preview (предпросмотр) может использовать Payload до публичного переключения;
- публичное переключение выполняется только после серверного импорта, проверки и подтверждения владельца.

После окончательного переключения недоступность Payload не должна автоматически возвращать старый опубликованный контент. Сайт должен использовать последнюю успешно сохранённую/закешированную Payload-версию или контролируемую ошибку. Иначе удалённая или скрытая информация может снова стать публичной.

## 9. Пошаговый план реализации

Каждый блок завершается проверкой и отдельным подтверждением перед следующим существенным изменением.

### Шаг 0. Документационное решение

Цель: убрать архитектурное противоречие и создать единый источник плана.

Работы:

- добавить этот документ;
- связать его с README (навигационным документом) Admin Platform (административной платформы);
- отметить прежнее решение «не использовать внешнюю CMS» как заменённое только для постепенно переносимого публичного контента;
- обновить текущий roadmap (дорожную карту) и Progress Log (журнал прогресса);
- не менять код, зависимости, базу или сервер.

Критерий выхода:

- документация ясно разделяет реализованное текущее состояние и утверждённый будущий пилот.

### Шаг 1. Изолированный локальный фундамент Payload

Цель: получить отдельную работающую CMS без подключения публичной страницы.

Работы:

- создать `content-studio/`;
- использовать совместимую зафиксированную версию Payload;
- настроить отдельные команды разработки, сборки и проверки;
- настроить безопасные environment variables (переменные окружения) без секретов в Git;
- создать Payload Users (пользователей Payload) и Media (медиатеку);
- настроить локальную базу и локальное файловое хранилище;
- проверить вход, загрузку, просмотр, замену и удаление тестового изображения;
- проверить production build (промышленную сборку) нового приложения;
- не менять текущий маршрут `Referenzen` (страницы примеров работ).

Критерий выхода:

- Payload запускается отдельно, а текущий сайт работает без изменений.

### Шаг 2. Структурированная модель Referenzen

Цель: перенести утверждённый контракт страницы в строгую схему Payload.

Работы:

- описать одну страницу `referenzen` без универсального конструктора;
- выделить повторяемые reference cases (кейсы выполненных работ) в структурированную коллекцию или строго типизированный массив после проверки текущего контракта;
- сохранить стабильные ID (идентификаторы) элементов между языками;
- настроить локализованные поля DE/EN/RU/TR/PL/AR;
- настроить немецкий как канонический язык;
- настроить RTL (направление справа налево) для AR;
- связать изображения с Media (медиатекой) через отношения, а не сырые URL;
- сделать Alt-тексты (альтернативные описания), видимость и обязательные поля проверяемыми;
- включить drafts (черновики), versions (версии) и restore (восстановление);
- настроить preview URL (адрес предпросмотра), пока без публичного подключения.

Критерий выхода:

- всю структуру `Referenzen` (страницы примеров работ) можно заполнить из Payload без ручного JSON и без редактирования кода страницы.

### Шаг 3. Экспорт текущего контента без записи

Цель: получить проверяемую копию текущей рабочей страницы.

Работы:

- читать текущие `CmsPage` и `CmsMedia` только через контролируемый read-only (только чтение) процесс;
- экспортировать DE/EN/RU/TR/PL/AR;
- сформировать JSON-артефакт экспорта и отчёт;
- проверить количество блоков, элементов, изображений, Alt-текстов (альтернативных описаний), ссылок, фильтров и видимых секций;
- не изменять рабочие записи и файлы.

Критерий выхода:

- экспорт повторяем, валиден и не выполняет ни одной записи в исходную систему.

### Шаг 4. Импорт копии в локальный Payload

Цель: наполнить новую CMS реальным контентом страницы.

Работы:

- сначала выполнить dry run (проверку без записи);
- сопоставить текущие поля со схемой Payload;
- скачать текущие публичные изображения только для чтения;
- загрузить копии в локальную Media (медиатеку);
- сохранить исходные URL и ID как migration metadata (служебные данные миграции), если это помогает проверке;
- импортировать все языки атомарно настолько, насколько позволяет выбранная модель;
- повторный запуск не должен создавать дубликаты.

Критерий выхода:

- локальная Payload CMS содержит проверенную копию текущей `Referenzen` (страницы примеров работ), а повторный импорт идемпотентен.

### Шаг 5. Адаптер публичной страницы и локальный переключатель

Цель: подключить локальную `Referenzen` (страницу примеров работ) к Payload без изменения серверного поведения.

Работы:

- ввести единый `getReferenzenContent` (получатель контента страницы) или эквивалентный адаптер;
- сохранить текущий legacy adapter (адаптер старой CMS);
- добавить payload adapter (адаптер новой CMS);
- нормализовать оба источника в один тип данных, который уже понимает React-страница;
- включить Payload только локальной переменной окружения;
- не добавлять неявный fallback (резервный возврат) во время проверки Payload;
- проверить, что production-настройка по умолчанию остаётся `legacy` (старой CMS).

Критерий выхода:

- локальная страница полностью отображает Payload-контент, а серверная конфигурация остаётся на старом источнике.

### Шаг 6. Локальная приёмка

Цель: доказать, что новая система решает исходную проблему управления контентом.

Обязательные сценарии:

- загрузка фотографии непосредственно из поля страницы;
- загрузка из модального окна медиатеки;
- поиск, фильтрация и сортировка;
- крупный просмотр и метаданные;
- явные Select / Cancel (выбрать / отменить), без случайной замены по одному клику;
- добавление, редактирование, удаление и перестановка элементов;
- Alt-тексты (альтернативные описания) по языкам;
- черновик, предпросмотр, публикация и восстановление версии;
- проверка всех шести языков;
- проверка AR RTL (арабского направления справа налево);
- проверка desktop/mobile (настольной и мобильной версии);
- проверка недоступности Payload;
- сравнение новой страницы с текущей публичной версией.

Критерий выхода:

- владелец самостоятельно проходит полный сценарий без вмешательства разработчика и подтверждает результат.

### Шаг 7. Безопасное размещение без публичного переключения

Цель: поставить Payload на сервер, не меняя публичный источник.

Работы:

- настроить серверное окружение Payload;
- создать отдельную логическую базу или схему в существующем PostgreSQL-кластере;
- настроить `payload/production/media/` в существующем Vercel Blob;
- применить проверенные миграции;
- создать владельца через безопасный bootstrap (первичную настройку) без вывода пароля;
- ограничить CORS (межсайтовые запросы), preview (предпросмотр) и административные адреса;
- оставить `REFERENZEN_CONTENT_SOURCE=legacy` (источник старой CMS) на публичном сайте;
- выполнить smoke tests (короткие проверочные тесты).

Критерий выхода:

- серверный Payload доступен только разрешённому владельцу, а публичная страница продолжает работать из старой CMS.

### Шаг 8. Серверный импорт и закрытый preview

Цель: проверить серверную Payload-версию до публикации.

Работы:

- повторить экспорт текущей рабочей страницы непосредственно перед импортом;
- выполнить dry run (проверку без записи);
- импортировать контент и копии медиа в Payload;
- проверить количество и контрольные суммы файлов;
- проверить все языки через защищённый preview (предпросмотр);
- проверить SEO, ссылки, видимость, изображения, Alt-тексты (альтернативные описания) и RTL (направление справа налево);
- зафиксировать результат приёмки.

Критерий выхода:

- серверная Payload-версия соответствует утверждённой локальной версии и текущему содержимому страницы.

### Шаг 9. Публичное переключение

Цель: сделать Payload единственным редактируемым источником `Referenzen` (страницы примеров работ).

Предусловия:

- локальная и серверная приёмка завершены;
- резервная копия подтверждена;
- старый источник доступен для rollback (отката);
- владелец отдельно подтвердил deployment (размещение) и переключение.

Работы:

- установить `REFERENZEN_CONTENT_SOURCE=payload`;
- выполнить controlled deployment (контролируемое размещение);
- проверить шесть публичных маршрутов;
- проверить кеширование и revalidation (обновление кеша);
- проверить опубликованные изображения;
- отметить старую `referenzen` в текущей CMS как read-only legacy (старую запись только для чтения), не удаляя её.

Критерий выхода:

- публичная страница работает из Payload, а откат не требует восстановления базы.

### Шаг 10. Наблюдение и решение о следующей странице

Цель: не расширять миграцию до доказанной стабильности пилота.

Работы:

- наблюдать ошибки API, загрузку медиа, публикацию и кеш;
- выполнить минимум один реальный цикл редактирования после запуска;
- проверить восстановление версии;
- проверить rollback (откат) в безопасном окружении;
- собрать замечания владельца по редакторскому UX (удобству управления контентом);
- только после этого выбирать следующую публичную страницу.

Критерий выхода:

- владелец принимает решение: продолжить перенос, доработать пилот или остановить расширение.

## 10. Модель данных пилота

Окончательные имена уточняются на Шаге 2 после сопоставления с текущей схемой, но минимальный набор должен включать:

### Payload Users (пользователи Payload)

- email;
- password hash (хеш пароля, управляемый Payload);
- role (роль);
- active (активность);
- timestamps (временные метки).

### Media (медиатека)

- файл и производные размеры;
- оригинальное имя;
- MIME type (тип файла);
- ширина и высота;
- локализованный Alt-текст (альтернативное описание);
- title (название);
- usage type (назначение);
- source/copyright (источник/авторские права), если применимо;
- migration source ID (идентификатор исходного файла миграции);
- where used (где используется) или обратная связь через отношения;
- soft-delete/governance policy (правила мягкого удаления и управления).

### Referenzen Page (страница примеров работ)

- slug / page key (служебный адрес / ключ страницы);
- локализованные Hero (главный экран), вводные и SEO-поля;
- видимость секций;
- CTA (кнопки действия);
- теги и фильтры;
- связанные cases (кейсы);
- статус публикации;
- версии и даты публикации.

### Reference Cases (кейсы выполненных работ)

- стабильный ID (идентификатор);
- локализованные название, описание, проблема, работа и результат;
- категория/фильтр;
- главное изображение;
- дополнительные изображения;
- порядок;
- видимость;
- SEO/Alt metadata (поисковые и альтернативные описания), где применимо.

## 11. Правила публикации

- `DRAFT` (черновик) может быть неполным.
- `PUBLISHED` (опубликовано) должен проходить серверную проверку.
- Обязательное изображение не публикуется без Alt-текста (альтернативного описания) для соответствующего языка.
- Неизвестные блоки не публикуются.
- Дублирующиеся стабильные ID (идентификаторы) блокируют публикацию.
- Скрытая секция не восстанавливается статическим контентом.
- Отсутствующая языковая версия не должна молча смешиваться с другим языком.
- Для ключевой страницы `Referenzen` (страницы примеров работ) перед полным публичным переключением требуются все шесть локалей.
- Публичный API возвращает только опубликованный контент.
- Preview (предпросмотр) черновика требует авторизации или короткоживущего подписанного токена.

## 12. Безопасность

Минимальные требования пилота:

- отдельный Payload secret (секрет Payload);
- HTTP-only secure cookies (защищённые файлы сессии, недоступные JavaScript);
- owner-only (только владелец) на первом этапе;
- deny by default (запрет по умолчанию) для административных операций;
- rate limiting (ограничение частоты) на вход;
- CORS allowlist (разрешённый список источников) только для известных адресов;
- `noindex` (запрет индексации) для административной панели и preview (предпросмотра);
- строгая проверка размера, MIME type (типа файла), расширения и сигнатуры загрузок;
- запрет смешивания публичной CMS-медиатеки с приватными вложениями клиентов;
- ограничение удаления медиа при наличии связей;
- журналирование публикации, восстановления и удаления;
- секреты только в environment variables (переменных окружения);
- отсутствие production credentials (рабочих учётных данных) в локальных файлах и логах.

До server deployment (размещения на сервере) требования должны быть сверены с:

- `docs/10_security_privacy/admin_security_and_governance.md`;
- `docs/10_security_privacy/security_guardrails.md`;
- `docs/10_security_privacy/security_checklist.md`.

## 13. Rollback (откат)

До завершения периода наблюдения:

- старая запись `CmsPage/referenzen` не удаляется;
- старые `CmsMedia` не удаляются;
- переключатель может быть возвращён на `legacy` (старую CMS);
- миграция Payload не должна менять исходные ID и файлы;
- deployment (размещение) считается неприемлемым без известной предыдущей рабочей версии;
- решение об удалении старого редактора принимается отдельным будущим документом и отдельным подтверждением владельца.

Rollback (откат) после переключения:

1. вернуть источник на `legacy` (старую CMS);
2. проверить шесть маршрутов;
3. зафиксировать причину;
4. не удалять неудачные Payload-данные до анализа;
5. исправить проблему в локальном/тестовом окружении;
6. повторить приёмку перед новым переключением.

## 14. Критерии успешного пилота

Пилот считается успешным только если владелец без помощи разработчика может:

- войти в Payload;
- открыть `Referenzen` (страницу примеров работ);
- загрузить изображение из поля и из медиатеки;
- найти, отфильтровать и открыть изображение крупно;
- явно выбрать или отменить выбор;
- заполнить и изменить Alt-тексты (альтернативные описания);
- заменить и удалить неиспользуемое изображение;
- получить запрет удаления используемого изображения;
- добавить, изменить, удалить и переставить кейс;
- скрыть и снова показать секцию;
- сохранить черновик;
- открыть preview (предпросмотр);
- опубликовать;
- восстановить предыдущую версию;
- проверить DE, EN, RU, TR, PL и AR;
- убедиться в корректном AR RTL (арабском направлении справа налево);
- вернуть страницу на старый источник по документированному rollback (откату).

## 15. Открытые решения, не блокирующие Шаг 1

- конечный серверный адрес Payload Admin (административной панели Payload);
- отдельная логическая база или схема `payload` в зависимости от возможностей текущего PostgreSQL-провайдера;
- точный срок периода наблюдения после переключения;
- следующая страница после успешной `Referenzen` (страницы примеров работ);
- будущий SSO (единый вход) между Ring Master и Payload;
- будущая судьба старого Page CMS после полного переноса публичных страниц.

Эти вопросы не требуют решения для локального изолированного Шага 1.
