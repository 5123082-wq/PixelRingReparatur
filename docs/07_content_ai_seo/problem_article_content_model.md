# Problem Article Content Model

Статус: proposal / active planning (предложение для активного планирования).

Дата: 2026-05-25

Назначение: зафиксировать, из каких смысловых блоков должна состоять problem article (статья о проблеме), какие блоки питают маленькую карточку, modal (модальное окно), full article (полную статью), JSON-LD (структурированные данные для поиска) и AI/GEO (оптимизацию для AI-ответов и генеративного поиска).

Этот документ не меняет текущую реализацию. Он задаёт целевую content model (контентную модель) для будущей доработки CMS (системы управления контентом), seed-файлов (скриптов загрузки данных) и редакторского процесса.

---

## 1. Главный принцип

Одна problem article (статья о проблеме) должна иметь один источник смысла и несколько поверхностей вывода:

- small card (маленькая карточка);
- modal (модальное окно);
- full article page (полная страница статьи);
- JSON-LD (структурированные данные для поиска);
- AI/GEO context (контекст для AI-ответов и генеративного поиска);
- CMS editor (редактор в системе управления контентом).

Сейчас часть смысла может жить в markdown draft (черновик в Markdown), часть в seed fields (полях скрипта загрузки данных), часть в fallback (резервной подстановке), часть в ручной mapping (ручной карте значений). Целевая модель должна уменьшить это расхождение.

---

## 2. Блоки статьи

### 2.1 `identity`

Служебная идентификация статьи.

Поля:

- `locale` - язык;
- `slug` - внутренний slug (служебный адрес);
- `publicSlug` - публичный slug (публичный адрес);
- `type` - тип статьи;
- `status` - статус публикации;
- `title` - основное название;
- `canonicalUrl` - canonical URL (канонический адрес);
- `seoTitle` - SEO title (заголовок для поиска);
- `seoDescription` - SEO description (описание для поиска).

Используется в:

- full article page (полная страница статьи);
- sitemap (карта сайта);
- canonical / hreflang (канонический адрес и языковые альтернативы);
- CMS editor (редактор в системе управления контентом).

### 2.2 `card`

Короткий слой для small card (маленькой карточки).

Поля:

- `cardTitle`;
- `cardSymptom`;
- `cardCauseText`;
- `cardSolutionText`;
- `cardPreviewLabel` при необходимости.

Задача: за несколько секунд помочь клиенту понять, похожа ли карточка на его проблему.

Не должно автоматически собираться из длинной статьи. Small card (маленькая карточка) слишком короткая, поэтому её текст лучше редактировать отдельно.

### 2.3 `shortAnswer`

Короткий ответ на главный вопрос статьи.

Задача: дать самостоятельный ответ в 2-4 предложения без точного диагноза и без рекламного давления.

Используется в:

- full article page (полная страница статьи), блок `Короткий ответ`;
- FAQPage JSON-LD (структурированные FAQ-данные для поиска), если вопрос/ответ подходят;
- AI/GEO context (контекст для AI-ответов и генеративного поиска);
- modal preview (краткое объяснение в модальном окне), если нужен сжатый обзор.

### 2.4 `symptoms`

Что видит клиент.

Примеры:

- вывеска полностью тёмная;
- не включается по таймеру;
- работает только часть букв;
- проблема появилась после дождя;
- свет мерцает, гаснет или меняет яркость.

Используется в:

- modal (модальное окно);
- full article page (полная страница статьи);
- AI/GEO context (контекст для AI-ответов и генеративного поиска).

### 2.5 `causes`

Вероятные причины, сформулированные осторожно.

Правило: причина не должна звучать как точный диагноз.

Используется в:

- modal (модальное окно), блок `Возможные причины`;
- full article page (полная страница статьи), блок `Частые причины`;
- internal assistant knowledge (внутренняя база знаний ассистента);
- AI/GEO context (контекст для AI-ответов и генеративного поиска).

### 2.6 `diagnosticQuestions`

Вопросы, которые помогают понять проблему без опасных действий.

Примеры:

- вся вывеска не светится или только одна зона;
- проблема появилась внезапно или постепенно;
- был ли дождь, мороз, скачок напряжения или ремонт рядом;
- есть ли фото общего вида и крупный план.

Используется в:

- AI assistant (AI-ассистент);
- CRM handoff (передача в CRM);
- modal (модальное окно), если нужен блок уточнений.

### 2.7 `safeChecks`

Безопасные проверки без вскрытия корпуса, контакта с проводами и работы на высоте.

Примеры:

- проверить обычный выключатель;
- проверить доступный автомат;
- проверить внешний таймер, если он доступен без вскрытия;
- посмотреть, есть ли питание у других приборов на этой линии;
- сделать фото и видео.

Используется в:

- full article page (полная страница статьи), блок `Что можно безопасно проверить`;
- modal (модальное окно), если нет более точного `selfRepairTips`;
- JSON-LD / AI context (структурированные данные и контекст для AI), если формулировки безопасны.

Важно: `safeChecks` не должен подменять `selfRepairTips`. Это разные блоки.

### 2.8 `selfRepairTips`

Отдельный блок `Советы по самостоятельному ремонту`.

Это не dangerous DIY instruction (опасная инструкция для самостоятельного ремонта). Это safety-bounded guidance (практические советы с границами безопасности).

Рекомендуемая внутренняя структура:

- `intro` - короткое объяснение, с чего начать;
- `withoutOpening` - что можно проверить без вскрытия;
- `technicalSpecialist` - что может проверить ваш технический специалист;
- `doNotDo` - чего не стоит делать;
- `qualificationNote` - нижняя сноска по квалификации и безопасному доступу.

Используется в:

- modal (модальное окно), обязательный отдельный блок;
- full article page (полная страница статьи), если публичная статья содержит этот раздел;
- CMS editor (редактор в системе управления контентом), как отдельная группа полей.

Правило: `selfRepairTips` должен быть полезнее, чем один disclaimer (предупреждение), но не должен учить опасному ремонту.

### 2.9 `urgentWarnings`

Срочные признаки.

Примеры:

- запах гари;
- искры;
- треск;
- нагрев;
- вода внутри;
- повреждённый кабель;
- повторно выбивает автомат;
- работа требует высоты или вскрытия корпуса.

Используется в:

- modal (модальное окно);
- full article page (полная страница статьи);
- AI assistant (AI-ассистент), чтобы не продолжать обычный сценарий при риске;
- CRM handoff (передача в CRM) как safety flag (признак риска).

### 2.10 `pixelringProcess`

Что обычно проверяет PixelRing.

Задача: показать профессиональную логику диагностики без обещания точного результата.

Используется в:

- modal (модальное окно), если нужен сервисный блок;
- full article page (полная страница статьи);
- AI/GEO context (контекст для AI-ответов и генеративного поиска).

### 2.11 `workScopeFactors`

Что влияет на объём работ.

Примеры:

- высота монтажа;
- доступ к вывеске;
- место блока питания;
- размер конструкции;
- количество букв и секций;
- состояние корпуса и герметичности;
- нужен ли демонтаж.

Используется в:

- full article page (полная страница статьи);
- request intake (приём заявки);
- CRM handoff (передача в CRM);
- AI assistant (AI-ассистент).

### 2.12 `fullArticle`

Длинный markdown content (содержимое в Markdown) для полной страницы.

Правило: `fullArticle` должен быть собран вокруг тех же смысловых блоков, а не противоречить им.

Он может быть более живым и подробным, но не должен становиться отдельным независимым источником истины, который расходится с `card`, `shortAnswer`, `causes`, `safeChecks` или `selfRepairTips`.

## 3. Карта вывода

| Surface (поверхность) | Источник |
|---|---|
| Small card (маленькая карточка) | `card.cardTitle`, `card.cardSymptom`, `card.cardCauseText`, `card.cardSolutionText` |
| Modal symptoms (симптомы в модальном окне) | `symptoms` |
| Modal causes (причины в модальном окне) | `causes` |
| Modal safe/self-repair block (безопасные действия и советы в модальном окне) | `selfRepairTips`, fallback (резервно) на `safeChecks` только временно |
| Modal urgency (срочность в модальном окне) | `urgentWarnings` |
| Modal service process (процесс PixelRing в модальном окне) | `pixelringProcess` |
| Full article (полная статья) | `shortAnswer`, `symptoms`, `causes`, `safeChecks`, `selfRepairTips`, `urgentWarnings`, `pixelringProcess`, `workScopeFactors`, `fullArticle` |
| JSON-LD (структурированные данные для поиска) | `shortAnswer`, безопасные FAQ (частые вопросы), canonical fields (канонические поля) |
| AI/GEO context (контекст для AI-ответов и генеративного поиска) | `shortAnswer`, `symptoms`, `causes`, `safeChecks`, `urgentWarnings`, `pixelringProcess`, `workScopeFactors` |
| Request intake / CRM handoff (приём заявки и передача в CRM) | `diagnosticQuestions`, `urgentWarnings`, `workScopeFactors` |

## 4. CMS editor direction

В CMS editor (редакторе системы управления контентом) problem article (статья о проблеме) не должна выглядеть как одно большое поле.

Целевой редактор должен показывать группы:

1. Identity & SEO (идентификация и поисковые поля).
2. Small card (маленькая карточка).
3. Short answer (короткий ответ).
4. Symptoms (симптомы).
5. Causes (причины).
6. Diagnostic questions (диагностические вопросы).
7. Safe checks (безопасные проверки).
8. Self-repair tips (советы по самостоятельному ремонту).
9. Urgent warnings (срочные признаки).
10. PixelRing process (как действует PixelRing).
11. Work scope factors (что влияет на объём работ).
12. Full article markdown (полная статья в Markdown).

Каждая группа должна иметь подсказку: где этот текст используется на сайте и зачем он нужен.

## 5. Safety rules for `selfRepairTips`

`selfRepairTips` должен разделять три уровня:

- `withoutOpening`: безопасно без вскрытия;
- `technicalSpecialist`: что может проверить ваш технический специалист;
- `doNotDo`: нельзя делать самостоятельно;
- `qualificationNote`: сноска о квалификации, профильных работах и безопасном доступе.

`technicalSpecialist` - общий слой для B2B-клиента (бизнес-клиента), у которого может быть ответственный сотрудник, техническая служба объекта или профильный обслуживающий специалист. Для электрических тем внутри этого блока можно уточнять `штатный электрик или технический специалист`. Для плёнок, корпуса, креплений, доступа, чистки и визуальных дефектов не нужно искусственно упоминать электрика.

Пример для `Вывеска не светится`:

- без вскрытия: проверить выключатель, автомат, внешний таймер, питание на той же линии, связь с дождём или работами;
- технический специалист: при подходящей квалификации проверить питание линии, автомат, вход 220/230 В, блок питания, выходное напряжение и доступные элементы управления;
- нельзя: вскрывать корпус без квалификации, работать под напряжением, делать скрутки, трогать влажные элементы, повторно включать при запахе гари или срабатывании автомата;
- сноска: любые работы с электрикой, корпусом, блоками питания, проводкой и высотой выполняются только при подходящей квалификации и безопасном доступе.

## 6. Migration approach

Не менять текущую публичную логику резко.

Рекомендуемый порядок:

1. Зафиксировать content model (контентную модель) в документации.
2. На одной статье `Вывеска не светится` проверить новую структуру как эталон.
3. Добавить explicit `selfRepairTips` (явный блок советов) для `no-light`, `flicking` и `uneven-light` без изменения UI (интерфейса).
4. После проверки владельцем спроектировать CMS editor groups (группы редактора CMS) и data model changes (изменения модели данных).
5. Только потом переносить существующие статьи из смешанной структуры в новую.

Критерий успеха: новая статья не может быть опубликована, если не заполнены блоки, от которых зависят small card (маленькая карточка), modal (модальное окно), full article (полная статья), JSON-LD (структурированные данные) и AI/GEO context (контекст для AI-ответов и генеративного поиска).

## 7. Open questions

- Должен ли `fullArticle` храниться как markdown (Markdown-разметка) или собираться из структурированных блоков с дополнительным rich text (форматированным текстом)?
- Нужно ли выделять `faqItems` (частые вопросы) отдельно от `shortAnswer`, чтобы JSON-LD (структурированные данные для поиска) не строился из неподходящих текстов?
- Должен ли `selfRepairTips` в CMS (системе управления контентом) быть массивом строк или структурой с подгруппами `withoutOpening`, `technicalSpecialist`, `doNotDo`, `qualificationNote`?
- Нужна ли validation rule (правило проверки), которая запрещает публикацию без `selfRepairTips`, `urgentWarnings` и `shortAnswer`?
- Как показывать Arabic / RTL (арабский язык и направление справа налево) в структурированном редакторе, чтобы группы не ломали ввод?
