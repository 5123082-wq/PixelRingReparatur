# План активации личного кабинета после создания заявки

## Назначение

Документ фиксирует целевой сценарий после создания публичного номера заявки `PR`.

Цель: не терять пользователя после создания заявки, сохранить Telegram как канал связи и переводить долгосрочный доступ к заявке в личный кабинет через подтвержденную электронную почту.

Базовые правила:

- номер `PR` подтверждает, что заявка создана;
- номер `PR` не является способом входа;
- полный личный кабинет доступен только после подтверждения электронной почты;
- Telegram остается каналом связи, но не становится полноценным интерфейсом отслеживания заявки;
- фразы вроде "отслеживать здесь в Telegram" запрещены, потому что такой функции сейчас нет.

## Короткое оглавление

1. Правила по каналам.
2. Сценарии создания заявки.
3. Telegram после выдачи `PR`.
4. Если электронная почта указана / не указана.
5. Страница статуса и активация личного кабинета.
6. WhatsApp и обычная электронная почта.
7. Изменения серверной логики.
8. Изменения интерфейса.
9. Тесты и порядок внедрения.
10. Риски и открытые решения.

## Главные продуктовые решения

### 1. Сайт и браузерный чат

Для публичной формы на сайте и для браузерного AI-чата электронная почта должна стать обязательной в момент создания заявки и выдачи номера `PR`.

Целевой сценарий:

1. Пользователь может читать сайт, писать в чат, загружать фото и описывать проблему без электронной почты.
2. Когда пользователь хочет создать заявку и получить номер `PR`, система требует электронную почту.
3. После успешного создания заявки:
   - номер `PR` показывается на экране;
   - создается ссылка привязки заявки к личному кабинету;
   - сразу отправляется письмо активации личного кабинета;
   - текущая browser-session cookie (кука текущей браузерной сессии) остается для безопасного доступа с этого же устройства.

Почему так:

- пользователь сайта может закрыть браузер и не вернуться;
- телефон без электронной почты слабее для восстановления доступа;
- электронная почта дает PixelRing надежный канал возврата пользователя к личному кабинету.

### 2. Telegram

Telegram должен остаться единственным каналом, где заявку можно создать без электронной почты.

Почему так:

- Telegram сам дает канал возврата в тот же диалог;
- бот может отправить номер `PR`, ссылку на проверку статуса и ссылку активации личного кабинета;
- при этом Telegram нельзя описывать как полноценный интерфейс отслеживания заявки.

Целевой сценарий:

1. Пользователь создает или формализует заявку через защищенную Telegram-форму.
2. Система выдает номер `PR`.
3. Бот отправляет:
   - номер `PR`;
   - ссылку на проверку статуса;
   - ссылку активации личного кабинета;
   - короткое объяснение, зачем нужен личный кабинет.
4. Если электронная почта была указана в защищенной Telegram-форме, система сразу отправляет письмо активации личного кабинета.
5. Если электронная почта не была указана, ссылка активации личного кабинета ведет на страницу, где пользователь добавляет электронную почту, получает код, подтверждает его, задает пароль и входит в личный кабинет.

Запрещенная логика:

- не писать, что пользователь может "отслеживать заявку в Telegram";
- не создавать новый интерфейс отслеживания внутри Telegram-чата;
- не смешивать обычный чат по заявке и проверку личности.

Правильная логика:

- "Статус заявки можно проверить по ссылке";
- "Диалог можно продолжить в Telegram";
- "Для долгосрочного доступа активируйте личный кабинет".

### 3. Уже авторизованный пользователь личного кабинета

Если пользователь уже вошел в личный кабинет, новая заявка не требует повторного письма активации.

Целевой сценарий:

1. Пользователь создает заявку из личного кабинета.
2. Система использует уже подтвержденную электронную почту аккаунта.
3. Новая заявка сразу привязывается к аккаунту.
4. Номер `PR` показывается в личном кабинете.
5. Дополнительное письмо активации не отправляется.

### 4. Ручная заявка в CRM

CRM (внутренняя система заявок) остается ручным управляемым сценарием для менеджера.

Целевой сценарий:

1. Менеджер создает заявку в CRM (внутренняя система заявок).
2. Если электронная почта клиента есть, менеджер видит действие "отправить ссылку активации личного кабинета".
3. На первом этапе лучше сделать это ручной кнопкой, а не автоматической отправкой, чтобы не слать письма по неполным или чувствительным заявкам.
4. Если электронной почты нет, менеджер может отправить ссылку активации личного кабинета через активный канал связи, когда клиент готов добавить электронную почту.

## Telegram после создания `PR`

### Если электронная почта была указана

После создания заявки бот отправляет одно сообщение с двумя кнопками.

Текст:

`Заявка PR-XXXX создана.`

`Мы отправили письмо для активации личного кабинета на указанный e-mail. Статус заявки можно проверить по ссылке.`

Кнопки:

- `Проверить статус`;
- `Открыть кабинет`.

Что делает каждая кнопка:

- `Проверить статус` открывает существующую страницу статуса или безопасную ссылку доступа к статусу;
- `Открыть кабинет` открывает ссылку активации личного кабинета или страницу входа, если доступ уже активирован.

Важно:

- не писать "отслеживать здесь";
- не обещать в Telegram то, чего нет в продукте;
- письмо активации личного кабинета не должно раскрывать приватные данные заявки.

### Если электронная почта не была указана

После создания заявки бот отправляет одно сообщение с двумя кнопками.

Текст:

`Заявка PR-XXXX создана.`

`Статус заявки можно проверить по ссылке. Для долгосрочного доступа к истории, документам и фотоотчетам активируйте личный кабинет: добавьте e-mail и подтвердите код.`

Кнопки:

- `Проверить статус`;
- `Активировать кабинет`.

Что делает каждая кнопка:

- `Проверить статус` открывает существующую страницу статуса или безопасную ссылку доступа к статусу;
- `Активировать кабинет` открывает ссылку активации личного кабинета;
- на странице активации пользователь вводит электронную почту, получает код, подтверждает его и задает пароль.

Важно:

- письмо не отправляется, пока пользователь сам не введет электронную почту;
- Telegram остается каналом связи;
- личный кабинет становится долгосрочным verified-доступом (доступом после подтверждения личности через электронную почту).

## Страница статуса и личный кабинет

Текущий экран статуса может показывать:

- безопасный статус заявки;
- чат по заявке, если есть действующая сессия или безопасный доступ;
- блок входа или активации личного кабинета.

Но этот экран не должен создавать впечатление, что Telegram уже является интерфейсом отслеживания.

Целевое изменение:

1. Добавить рядом со статусом явный блок активации личного кабинета.
2. Если у заявки есть активная ссылка активации личного кабинета, показывать:
   - заголовок: `Активируйте личный кабинет`;
   - текст: `Сохраните доступ к заявке, истории, документам и фотоотчетам. Укажите e-mail и подтвердите код.`;
   - кнопку: `Активировать кабинет`.
3. Если пользователь уже вошел в личный кабинет, показывать:
   - кнопку: `Перейти в кабинет`.
4. Если ссылка активации истекла, показывать нейтральное сообщение:
   - `Ссылка доступа истекла. Запросите новую ссылку у PixelRing.`

Верификацию не нужно делать внутри обычного чата на сайте.

Почему:

- чат нужен для общения по заявке;
- активация личного кабинета является проверкой личности;
- если смешать эти сценарии, пользователь не поймет, где переписка, а где вход;
- с точки зрения безопасности лучше держать верификацию в отдельном claim-flow (сценарии привязки заявки к личному кабинету).

Правильный путь:

- экран статуса показывает CTA (призыв к действию) для активации личного кабинета;
- CTA (призыв к действию) открывает существующий claim-flow (сценарий привязки заявки к личному кабинету);
- claim-flow (сценарий привязки заявки к личному кабинету) обрабатывает электронную почту, код, пароль и доступ к заявке.

## WhatsApp и обычная электронная почта

### WhatsApp

WhatsApp не должен считаться полноценным автоматическим каналом создания заявки, пока нет реальной интеграции.

Как лучше сделать:

1. На сайте можно оставить WhatsApp как быстрый канал связи.
2. Если клиент хочет получить номер `PR`, менеджер или будущий бот отправляет защищенную ссылку на форму заявки.
3. Если заявка создается через сценарий сайта, электронная почта обязательна.
4. Если менеджер создает заявку вручную по переписке в WhatsApp, активация личного кабинета идет через CRM (внутреннюю систему заявок).

Граница публичного обещания:

- не обещать автоматическое отслеживание через WhatsApp;
- говорить, что WhatsApp удобен для быстрой связи и координации;
- создание заявки с номером `PR` вести через защищенную форму или CRM (внутреннюю систему заявок).

### Обычная электронная почта

Обычный `mailto:` не должен считаться полноценным каналом автоматического создания заявки.

Как лучше сделать:

1. Оставить адрес электронной почты как вторичный контакт для нестандартных случаев.
2. Основные CTA (призывы к действию) на сайте должны вести в форму заявки или чат.
3. Если клиент написал письмо, менеджер может:
   - создать заявку вручную в CRM (внутренней системе заявок);
   - отправить защищенную ссылку на форму заявки;
   - отправить ссылку активации личного кабинета после создания заявки.
4. Автоматический email-parser (парсер входящих писем) можно планировать позже, но не включать в первый этап.

## План серверной логики

### Шаг 1. Явная политика контакта по каналу

Нужно добавить правило не на уровне одного поля формы, а на уровне серверной логики.

Целевые правила:

- `WEBSITE_FORM`: электронная почта обязательна для создания `PR`;
- `WEBSITE_CHAT`: электронная почта обязательна для создания `PR`;
- `TELEGRAM`: электронная почта необязательна;
- `PORTAL`: используется уже подтвержденная электронная почта личного кабинета;
- `CRM_MANUAL`: решение принимает менеджер.

Техническое направление:

- оставить текущий `parseContact` для разбора телефона и электронной почты;
- добавить более высокий валидатор политики канала;
- не полагаться только на интерфейс, потому что API (серверные маршруты) должны сами запрещать неправильный сценарий.

Вероятные файлы:

- `signage-service/src/app/api/contact/route.ts`;
- `signage-service/src/lib/request-intake.ts`;
- `signage-service/src/app/api/telegram/intake/submit/route.ts`;
- `signage-service/src/lib/telegram-intake.ts`;
- тесты в `signage-service/scripts/`.

### Шаг 2. Письмо активации после заявки с сайта

После создания заявки через сайт или браузерный чат система должна сразу отправить письмо активации личного кабинета.

Условие:

- письмо отправляется только если заявка создана успешно;
- электронная почта уже обязательна для этих каналов;
- письмо не должно открывать приватные данные без подтверждения кода.

Техническое направление:

- использовать существующую инфраструктуру отправки писем для личного кабинета;
- при необходимости добавить отдельную вспомогательную функцию для письма-приглашения;
- не смешивать письмо с кодом и письмо-приглашение, если это усложнит пользовательский сценарий.

Возможные варианты:

1. Письмо-приглашение содержит ссылку активации личного кабинета. Затем пользователь вводит код.
2. Письмо сразу содержит код для активации личного кабинета. Тогда экран должен быть понятным и не требовать повторной отправки кода.

Рекомендуемый первый вариант:

- письмо содержит ссылку активации личного кабинета;
- код отправляется после запуска claim-flow (сценария привязки заявки к личному кабинету);
- так проще сохранить текущую модель безопасности.

Вероятные файлы:

- `signage-service/src/lib/email/portal-claim-email.ts`;
- `signage-service/src/lib/request-intake.ts`;
- `signage-service/src/app/api/contact/route.ts`.

### Шаг 3. Telegram должен получать ссылку активации личного кабинета

После создания `PR` через Telegram нужно возвращать и отправлять пользователю не только ссылку статуса, но и ссылку активации личного кабинета.

Техническое направление:

- `submitTelegramIntake` должен создавать или получать ссылку активации личного кабинета;
- результат должен вернуть эту ссылку в `api/telegram/intake/submit`;
- Telegram-сообщение должно получить вторую кнопку;
- текст сообщения должен зависеть от того, есть ли электронная почта.

Вероятные файлы:

- `signage-service/src/lib/telegram-intake.ts`;
- `signage-service/src/app/api/telegram/intake/submit/route.ts`;
- `signage-service/src/app/api/telegram/webhook/route.ts`.

### Шаг 4. Ветка Telegram с электронной почтой

Если в Telegram-форме указан e-mail:

1. Создать `PR`.
2. Создать ссылку активации личного кабинета.
3. Отправить письмо активации личного кабинета.
4. Отправить в Telegram номер `PR`, кнопку статуса и кнопку кабинета.

Если письмо не отправилось:

- заявка не должна откатываться;
- Telegram все равно должен показать ссылку активации личного кабинета;
- ошибка отправки письма должна попасть в лог для менеджерской проверки;
- пользователю нельзя показывать детали SMTP (почтового сервера) или провайдера.

### Шаг 5. Ветка Telegram без электронной почты

Если в Telegram-форме указан только телефон или другой не-email контакт:

1. Создать `PR`.
2. Создать ссылку активации личного кабинета.
3. Не отправлять письмо.
4. Отправить в Telegram номер `PR`, кнопку статуса и кнопку активации кабинета.
5. На странице активации попросить электронную почту и запустить проверку кодом.

Граница безопасности:

- Telegram дает канал возврата;
- полный личный кабинет все равно требует подтвержденную электронную почту.

### Шаг 6. Истекшие ссылки активации

Если ссылка активации личного кабинета истекла:

- показывать нейтральное сообщение об истечении;
- не раскрывать, есть ли у заявки электронная почта или аккаунт;
- предложить запросить новую ссылку у PixelRing;
- позже можно добавить команду или кнопку в Telegram для повторной выдачи ссылки по активной заявке.

## План интерфейса

### Поля форм после изменений

После изменения правил нужно уйти от одного общего поля `Контакт`, потому что оно скрывает важное различие между обязательной электронной почтой и дополнительным телефоном.

#### Форма сайта

Поля:

1. `Имя / компания` — необязательно.
2. `E-mail` — обязательно.
3. `Телефон` — необязательно.
4. `Адрес / место` — необязательно.
5. `Что произошло` — обязательно.
6. `Фото / видео` — необязательно.

Правило:

- заявка с номером `PR` через форму сайта не создается без электронной почты;
- телефон можно оставить только как дополнительный контакт;
- телефон не заменяет электронную почту для сайта;
- если пользователь хочет оставить телефон, он вводит его во второе отдельное поле.

Текст ошибки:

`Укажите e-mail, чтобы создать заявку и получить доступ к личному кабинету. Телефон можно добавить как дополнительный контакт.`

Альтернатива для пользователя без электронной почты:

`Без e-mail заявку с номером PR можно оформить через Telegram, где диалог остается каналом связи.`

#### Браузерный чат

Поля inline-формы заявки в браузерном чате должны совпадать с формой сайта:

1. `Имя / компания` — необязательно.
2. `E-mail` — обязательно.
3. `Телефон` — необязательно.
4. `Адрес / место` — необязательно.
5. `Тип заявки` — необязательно или предзаполнено из чата.
6. `Описание проблемы` — обязательно или предзаполнено из чата.
7. `Фото / видео` — необязательно.

Правило:

- чат может собирать описание, фото и адрес без электронной почты;
- создание `PR` через браузерный чат требует электронной почты;
- телефон остается дополнительным контактом;
- если в чате уже найден телефон, его можно предзаполнить в поле `Телефон`, но нельзя считать достаточным для создания заявки на сайте.

Текст ошибки:

`Для создания заявки укажите e-mail. Телефон можно оставить дополнительно для звонка специалиста.`

#### Защищенная Telegram-форма

Поля:

1. `Имя / компания` — необязательно.
2. `E-mail` — необязательно, но рекомендовано.
3. `Телефон` — необязательно.
4. `Адрес / место` — необязательно.
5. `Тип заявки` — необязательно.
6. `Что произошло` — обязательно.
7. `Фото / видео` — необязательно.

Правило:

- Telegram может создать `PR` без электронной почты;
- Telegram может создать `PR` без телефона, если сам Telegram-чат является каналом возврата;
- если электронная почта указана, сразу отправляется письмо активации личного кабинета;
- если электронная почта не указана, бот отправляет кнопку `Активировать кабинет`, где пользователь добавит e-mail позже;
- телефон в Telegram остается полезным операционным контактом, но не является доступом в личный кабинет.

Пояснение под полем `E-mail`:

`Если укажете e-mail, мы сразу отправим письмо для активации личного кабинета. Если нет, вы сможете добавить e-mail позже по ссылке.`

Пояснение под полем `Телефон`:

`Телефон нужен только для связи по заявке. Личный кабинет активируется через e-mail.`

#### Личный кабинет

Форма новой заявки в личном кабинете не должна спрашивать электронную почту заново.

Поля:

1. `Тип заявки` — желательно.
2. `Адрес / место` — необязательно.
3. `Что нужно сделать` — обязательно.
4. `Фото / видео` — необязательно.

Правило:

- электронная почта берется из подтвержденной сессии личного кабинета;
- телефон можно добавить позже как поле профиля или контакт заявки, но не как обязательный вход в этот сценарий.

#### CRM (внутренняя система заявок)

CRM (внутренняя система заявок) должна хранить электронную почту и телефон как отдельные поля.

Поля:

1. `Имя / компания`.
2. `E-mail`.
3. `Телефон`.
4. `Канал происхождения`.
5. `Адрес / место`.
6. `Описание`.

Правило:

- менеджер может создать заявку с электронной почтой, телефоном, обоими полями или без них, если это операционно нужно;
- личный кабинет все равно активируется только через подтвержденную электронную почту;
- если электронной почты нет, CRM (внутренняя система заявок) должна показывать, что доступ в личный кабинет еще не активирован.

### Форма сайта

Изменить контактное поле:

- текущий `Контакт` должен стать `E-mail для заявки`;
- телефон должен быть отдельным необязательным полем;
- ошибка должна объяснять, что электронная почта нужна для создания заявки и доступа к кабинету.

Предлагаемый текст:

- label (подпись поля): `E-mail для заявки`;
- пояснение: `На этот e-mail придет ссылка для активации личного кабинета.`;
- error (ошибка): `Укажите e-mail, чтобы создать заявку и получить доступ к личному кабинету.`

### Браузерный чат

Inline-форма заявки в браузерном чате должна следовать тому же правилу, что форма сайта.

Изменения:

- убрать выбор `phone/email` (телефон/e-mail) как взаимоисключающий режим;
- требовать электронную почту;
- оставить телефон отдельным необязательным полем;
- после успеха показывать номер `PR`, статусную ссылку и ссылку активации личного кабинета;
- если письмо отправлено, показывать короткое подтверждение.

### Защищенная Telegram-форма

Для Telegram лучше разделить `E-mail` и `Телефон`, но сделать оба поля необязательными.

Дополнить пояснение:

`Если укажете e-mail, мы сразу отправим письмо для активации личного кабинета. Если нет, вы сможете добавить e-mail позже по ссылке.`

Почему:

- Telegram остается быстрым каналом;
- пользователь понимает преимущество электронной почты;
- сценарий без электронной почты не блокируется.
- телефон не смешивается с электронной почтой и остается отдельным операционным контактом.

## Правила безопасности

1. Номер `PR` никогда не дает приватный доступ сам по себе.
2. Ссылка статуса показывает только безопасный статус, если нет подтвержденной сессии или другого разрешенного доказательства.
3. Ссылка активации личного кабинета запускает проверку, но не открывает приватные данные.
4. Код на почту должен быть короткоживущим, одноразовым, ограниченным по попыткам и храниться только как хэш.
5. Сессия личного кабинета должна храниться в HTTP-only cookie (куке, недоступной JavaScript).
6. Telegram chat id (идентификатор Telegram-чата) нельзя раскрывать публично или передавать AI-ассистенту как персональные данные.
7. Ошибка отправки письма не должна раскрывать пользователю детали SMTP (почтового сервера), API (интерфейса провайдера) или токенов.
8. В логах нельзя хранить пароли, коды, токены и полные ссылки активации, если этого можно избежать.

## Тесты и проверка

### Автоматические тесты

Нужны тесты на сценарии:

1. Форма сайта с телефоном без электронной почты не создает `PR`.
2. Браузерный чат с телефоном без электронной почты не создает `PR`.
3. Форма сайта с электронной почтой создает `PR`, ссылку активации личного кабинета и попытку отправки письма.
4. Браузерный чат с электронной почтой создает `PR`, ссылку активации личного кабинета и попытку отправки письма.
5. Telegram с электронной почтой создает `PR`, ссылку активации личного кабинета и попытку отправки письма.
6. Telegram без электронной почты создает `PR` и ссылку активации личного кабинета, но не отправляет письмо.
7. Ссылка активации личного кабинета не открывает приватные данные без подтверждения кода.
8. Номер `PR` без контакта или с неподтвержденным контактом не открывает личный кабинет.

### Ручная проверка

Проверить после реализации:

1. Форма сайта + только телефон: заявка не создается, ошибка понятная.
2. Форма сайта + электронная почта: `PR` создан, письмо отправлено, ссылка статуса работает.
3. Браузерный чат + только телефон: заявка не создается, ошибка понятная.
4. Браузерный чат + электронная почта: `PR` создан, письмо отправлено, карточка успеха работает.
5. Telegram-форма + телефон: `PR` создан, бот прислал статус и активацию кабинета, письмо не отправлено.
6. Telegram-форма + электронная почта: `PR` создан, бот прислал статус и кабинет, письмо отправлено.
7. Telegram-кнопка `Активировать кабинет` без электронной почты: страница просит e-mail, отправляет код, дает задать пароль и открывает заявку в кабинете.
8. Уже авторизованный пользователь личного кабинета создает заявку: заявка появляется в кабинете без повторного письма активации.
9. CRM (внутренняя система заявок) вручную создает заявку: менеджер может выдать ссылку активации личного кабинета.

## Риски и открытые решения

### Риски

- Письма не будут доставляться, если SMTP (почтовый сервер) настроен неправильно.
- Обязательная электронная почта на сайте может уменьшить количество слабых заявок, но повысит качество возврата и активацию личного кабинета.
- Пользователь Telegram без электронной почты может проигнорировать ссылку активации личного кабинета.
- Истекшие ссылки активации личного кабинета требуют понятного сценария обновления.
- WhatsApp и обычная электронная почта остаются ручными каналами до интеграции.

### Открытые решения

1. Должен ли пользователь Telegram сам запрашивать новую ссылку активации личного кабинета после истечения старой?
2. Должна ли CRM (внутренняя система заявок) автоматически отправлять ссылку активации при наличии электронной почты, или сначала оставить ручную кнопку менеджера?
3. Какие точные темы и тексты письма активации личного кабинета нужны для DE, EN, RU, TR, PL и AR?
